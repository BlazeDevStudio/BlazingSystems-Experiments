# Offline stem separation research — 2026-10-23

## Recommendation and scope

Keep separation out of playback startup and the fast note preview. The next useful experiment is a separate, cancellable **vocals/accompaniment** job using the published sherpa-onnx Spleeter 2-stem ONNX conversion. It is a real engine candidate with small published artifacts and ARM CPU measurements, but it has not been compiled, run, or validated in this app. It does not satisfy separate drums/piano/voice controls. Treat a full multi-instrument feature as a subsequent stage with its own quality and phone-performance evidence.

Use Demucs as an offline reference for separation quality and Spleeter 5-stem as a piano-capable comparison. Do not ship an unmeasured Demucs model in the APK or claim parity with a commercial separation service. A TFLite MDX conversion is also available for investigation; its provenance and performance need checking before it displaces the simpler 2-stem pilot.

This is a primary-source review, checked on 2026-10-23. No weights were downloaded, no unknown binaries were executed, and no Android separation benchmark was run. All proposed budgets below are acceptance targets, not measured results. This document implements no app behavior.

The design constraint is [mixed media and fast note preview](../superpowers/specs/2026-10-23-mixed-media-fast-notes-design.md). The existing app uses a 22,050 Hz Basic Pitch path (`analysis/AnalysisRepository.kt`, `analysis/ModelRunner.kt`) and a 4,096-sample live tracker (`tuning/LiveNoteTracker.kt`). Keep those paths usable independently of separation. The model’s complete mix analysis and a separated-stem analysis must have distinct cache identities.

RTF means processing time divided by audio duration; below 1 indicates throughput faster than the input duration in that particular experiment. Throughput, first-result latency, and causal live operation are different properties.

The Demucs paper’s parameter range corresponds to about 103–158 MiB for raw FP32 parameters alone (calculation: parameters × 4 / 1,048,576). This is an illustration, not a checkpoint-download claim. Its README’s multi-gigabyte **GPU** figures must not be relabeled as Android CPU RAM requirements. `--two-stems` still performs full separation and mixes outputs afterward, so that flag does not establish a lightweight two-source implementation. [S1, S3]

### Smaller research models are a watchlist, not a deployable dependency

- **Band-SCNet, Interspeech 2025:** authors report four-source separation, 2.59M parameters, 17.59 GFLOPs/s and 92 ms algorithmic latency. The latter is not measured Android wall-clock latency. Raw FP32 parameter storage would be about 9.9 MiB. No author-published, licensed Android-ready checkpoint/export was verified in this review. [S9]
- **Moises-Light, arXiv v1 (2025):** the paper reports separate per-source models, approximately 5M × 4 or a smaller approximately 2M × 4 configuration, not one 2M model that produces every stem. It also acknowledges perceptible artifacts that SDR does not reflect. A paper or an unofficial reimplementation is insufficient evidence of distributable production weights. No author-published Android export with a confirmed weight license was verified here. [S10]

Neither research result supplies a verified piano model for this feature. “Lightweight” by parameter count does not imply small activation memory, fast STFT, or acceptable performance alongside video rendering.

## What separation can and cannot improve

Spotify describes Basic Pitch as polyphonic and instrument-agnostic, while saying it works best on one instrument at a time. This supports a **hypothesis** that separating a voice from backing, or removing drums before tonal estimation, may improve note estimates. It does not establish that this app’s Basic Pitch model will gain accuracy on every separated output. [S14]

Evaluate several failures explicitly: voice bleed creates duplicate notes in accompaniment; removed harmonics cause octave mistakes; tonal residue creates false notes; onset smearing shifts note starts; reverberation and sustained piano tails extend notes; stereo phase cancellation during mono conversion can remove useful signal. A separator can improve audible isolation while degrading transcription. A separated vocal group may still contain multiple singers, and “other” may contain several polyphonic instruments. Notes need source provenance; do not union every stem’s notes and count bleed as additional instruments.

Drums generally need an onset/percussion detector, not a claim that each transient has a stable musical pitch. For a piano-specific feature, evaluate a model that actually predicts piano, with annotated piano examples and bleed tests. A four-source “other” output is not an isolated piano.

HPSS uses time/frequency median filtering to form harmonic and percussive components, with an optional residual. These are signal properties, not instrument identities. A piano has both attacks and sustained harmonics; voice and pitched percussion can cross these components. Frequency bands similarly group frequencies, not sound sources. If an HPSS baseline is added, label it **harmonic/percussive filtering** and never present its outputs as detected piano/drums/vocals. [S15]

## Proposed integration contract for the real 2-stem pilot

This is a proposed data boundary, not an implemented API. Audit the chosen engine’s exact windowing, normalization and padding requirements first; do not assume it can consume the existing 22,050 Hz mono tracker buffer.

| Record | Required contents / invariant |
|---|---|
| `SeparationModelManifest` | Engine and export version; original checkpoint URL; SHA-256 for every artifact; original and conversion licenses/notices; sample rate; channel count/layout; exact stem order; input/output shapes and dtypes; STFT/window/hop/context; normalization and reconstruction rules. Capabilities must enumerate actual predicted stems. |
| `SeparationRequest` | Source identity and selected audio-track identity; source-generation token; source-time sample range; model fingerprint; cancellation token; explicit analysis purpose. Do not use playback-speed-adjusted wall time as source time. |
| `StemSegment` | Estimated stem label; source start sample and valid half-open range; sample rate/channels; exact frame count; model fingerprint; delay/padding removal; shared gain metadata; immutable PCM/cache location. Avoid independent stem loudness normalization that changes relative energy. |
| `SeparationState` | Not requested / queued / running / ready / cancelled / unsupported / failed, plus completed source ranges. “Ready” requires atomic complete outputs for that range. Failure leaves normal playback and mix analysis available. |
| `StemAnalysisResult` | Source + generation + stem + model + transcription configuration + source-time range, with estimated notes/onsets and existing confidence semantics. Do not fabricate a separator confidence score that the model does not supply. |

Start with one background worker and bounded excerpts (at most 30 seconds for the pilot). Measure and document the engine’s required context before implementing overlap/reconstruction. A job result from an old seek, selected source, model or audio track must never replace the current result. Cancel between engine calls and discard obsolete native output; if in-flight native execution cannot be interrupted, document that limitation and bound the call length. Keep reference-counted source leases until calls finish, then close sessions, tensors and temporary files.

Decode at the separator’s required rate/channels, preserve source timestamps, then downmix and resample **the separated output** for the current 22,050 Hz transcription path. Test delay and boundary bookkeeping with impulses and known note starts. The first iteration should retain stems in an evictable analysis cache and keep audible playback on the original single Media3 session. No automatic song upload, full-file startup dependency, silent substitution of stem audio, or fake separation switch belongs in this stage.

## Concrete next-stage evaluation

1. **Pin and inspect a real artifact.** Use sherpa-onnx v1.13.8, commit `11afbd009a7f8c08f4bcf2fc1b265d0df4670fbf`, as a candidate engine pin, not a claim of verified integration. Its general Android AAR exists; verify that the selected native build exports source-separation symbols and whether Kotlin bindings exist. If absent, make the small JNI/C API bridge explicit or select and document a later audited commit. Current C API docs are on `master` and are not proof about that release. [S6, S7]
2. **Establish model identity.** Record the actual SHA-256 and unpacked bytes for the Spleeter FP16 package and each ONNX file. The `source-separation-models` release tag currently points to `901b3f01500523010071a9ffd2744cab3bd30e8c`, but release assets can be replaced independently; that tag is not an immutable model pin. Check conversion inputs and licenses before bundling. [S16]
3. **Host correctness before phone tuning.** On authorized short audio, compare the original engine and converted outputs, validate silence/mono/stereo/44.1/48 kHz inputs, source order, sample counts, channel layout, gain, finite values and boundary continuity. Verify actual operators; a successful ONNX-to-TFLite conversion is not numerical equivalence. LiteRT select-TF operators may add a large runtime dependency. [S17]
4. **Run an annotated pitch comparison.** Use at least 20 held-out excerpts covering solo piano, piano+voice, dense mixes, isolated percussion, multiple singers, low bass, reverb, silent and instrumental passages. Use self-recorded/synthetic material or a licensed multitrack corpus with known notes. Compare mix → Basic Pitch, HPSS harmonic → Basic Pitch, Spleeter stems → Basic Pitch, and selected reference stems. Freeze transcription thresholds. Report per-excerpt onset-note F1 (50 ms onset / 50 cent pitch tolerance), frame multipitch precision/recall, octave errors, duplicate notes and false notes in silent target stems. Keep a separate percussion-onset metric. Report confidence intervals or the per-excerpt spread; mean SDR alone does not answer the note question.
5. **Measure physical Android devices during real playback.** Include a constrained API26-class phone and a recent API36 phone, each with video+visualizer running. Measure cold/warm model load, first completed segment, RTF, native+Java peak PSS, APK/installed bytes, disk cache, dropped frames/audio underruns, cancellation, battery/thermal behavior over ten minutes, and recovery after low-memory pressure. Start on CPU with one thread; compare two threads and quantized variants only after correctness passes. Do not infer NNAPI/GPU delegation from a filename.
6. **Use explicit release gates.** Proposed pilot targets: no new dependency before playback or the first quick note; no increase in audio underruns; <150 MiB extra peak PSS for the 2-stem job; warm RTF ≤0.5 on the reference midrange phone; no published segment from an obsolete generation; clean API26/API36 native loading and lifecycle tests. Promote “improved notes” only if the target-case note F1 improves by at least 5 percentage points without >2-point aggregate regression or increased silence false positives. If the speed gate fails, offer only an explicit offline analysis job; if the note gate fails, do not replace the default note path.

The current material blockers are verified artifact provenance/hashes, the exact Android binding at a pinned engine version, measured peak phone memory/thermal performance, and evidence that downstream notes improve. Reliable piano isolation remains a separate quality blocker. None is resolved by this research document.
